# kintone開発 共通ナレッジ

複数のkintoneプロジェクトを横断する、特定アプリに限定されないkintoneプラットフォーム
全般の挙動・罠・設計パターンを集約するファイル。

- 現在対象: SMC工事管理（app34,37,38,40,43,45,54,55）
- SMC設備機器台帳（旧app31,32）は2026-09時点でサード社製「管理ロイド」への移行に伴い
  kintone運用を終了。過去の発見（下記2026-07-19の項目など）はkintone自体の挙動として
  引き続き有効なため残しているが、当該アプリはもう存在しない。

## Claudeへの指示（このファイルを開いた全セッション共通）

- **作業開始時**: このプロジェクト固有のCLAUDE.md（または同等のドキュメント）に加えて、必ずこのファイルにも目を通すこと
- **新しい発見があった時**: 「このアプリだけの話」ではなく「kintoneというプラットフォーム自体の挙動・罠・汎用的な設計パターン」だと判断したら、都度このファイルに追記すること（個別アプリのフィールド名・業務ロジックはプロジェクト側のCLAUDE.mdに書き、ここには書かない）
- 追記時は「### 発見日 — 短いタイトル」の見出し＋本文（背景・具体的な症状・対処法）の形式で統一する
- このファイルは自動で他セッションに反映されるわけではない（次にそのプロジェクトのセッションを開いた時に読み込まれる形）。リアルタイム同期ではないことを理解した上で運用する

### 2026-07-19 — カスタマイズファイルを削除→再アップロードすると実行順序が最後尾に移動する
kintoneの「JavaScript / CSSでカスタマイズ」画面は、アップロードされたファイルを**一覧の並び順どおりに実行**する（`GET /k/v1/app/customize`のdesktop.js配列順と一致）。既存ファイルを削除して同名ファイルを再アップロードする「差し替え」を行うと、そのファイルは一覧の**最後尾に移動**し、他のファイルとの実行順序が変わる。

複数のカスタムJSが同じDOM領域（例: `kintone.app.getHeaderMenuSpaceElement()`）に依存し合っている場合、この順序変化だけで「後発スクリプトが割り込み先を見失い、ボタン配置が崩れる」といった事故が起きる（SMC設備機器台帳で実際に発生・実機確認で検知し復旧）。

**対処**: 複数スクリプトが同じ領域を共有する場合は、順序に依存しない共通マウントポイント（`window.SMCToolbar`のような、globalに公開したregistryオブジェクトへ`mount(key, order, element)`で登録する方式）を用意し、各スクリプトが「自分の要素と表示順」だけを登録すればよい設計にする。ファイル差し替え後は必ず実機でボタン配置を確認し、崩れていたらファイル一覧の並び替え（ドラッグ）で応急対応できる。

### 2026-07-19 — CSS `zoom` と `position:sticky` の併用はスクロール中に描画ちらつきを起こす
一覧表示を80%等に縮小する目的で`zoom`プロパティを使うと、`position:sticky`で固定した列と組み合わせた際、スクロール中に固定列のセルが一瞬別の行の内容のまま描画される（Chromeの描画ちらつき）ことがある。スクロールを止めれば正しい表示に戻るため恒久的なバグではないが、ユーザー体験上は「ズレて見える」。

**対処**: `zoom`は使わず、セル内側の要素（フォントサイズ・パディング）を直接縮小率どおりに指定する。レイアウトの再計算が発生しないため`position:sticky`との組み合わせでも描画ちらつきが起きない。

### 2026-07-19 — フィールドID（数値）とフィールドコード（文字列）の安定性の違い
kintoneのフィールドには、作成時に割り当てられる**フィールドID**（数値、例: `5521938`）と、**フィールドコード**（文字列、例: `機器番号`）の2種類の識別子がある。フィールド名（表示ラベル）を管理画面で変更すると、フィールドコードは追従して変わることがある（明示的にコードを固定していない場合）。一方でフィールドIDは作成時から不変。

カスタムJSで`th.label-<フィールドID>`・`td.value-<フィールドID>`のようにDOM上のクラス名からフィールドを特定する場合はフィールドIDベースの方が、フィールド名変更に強く壊れにくい。逆にAPIクエリ文字列（`q`パラメータ）はフィールドコードでしか書けないため、そちらは名前変更時の追従修正が必要になる。

### 2026-07-19 — ルックアップのコピー先フィールドはAPI経由の直接PUTが「見かけ上成功」して実際は反映されない
他アプリを参照するルックアップフィールドの「コピー先」に設定されているフィールドは、PUT APIで直接値を書き込むと`$revision`は加算されて一見成功したように見えるが、直後にGETすると値が元に戻っている。

**対処**: 該当フィールドをルックアップの「コピーするフィールドの設定」から外し、通常のフィールドとして独立させる。以降はAPIからの直接PUTが正しく反映される。同一参照キー（例: 機器番号）で複数レコードが存在する一対多の関係では、そもそも標準ルックアップの「参照キー一意」の前提が崩れるため、この対処が必要になりやすい。

### 2026-08-02 — `<td>`に`display:flex`を直接指定すると`rowspan`（行結合）が効かなくなる
一覧テーブルの`<td>`要素そのものに`display: flex`を指定すると、ブラウザがそのセルを「表セル（table-cell）」として扱わなくなり、CSSのテーブルレイアウトアルゴリズムから外れる。結果、`rowspan`属性を付けても複数行にまたがる高さで描画されず、最初の1行分の高さにしか広がらない（見た目上は「結合されているはずの2行目以降が空白 or 内容が上段だけに寄って見える」）。

**対処**: `<td>`自体はdisplay指定なし（既定のtable-cell）のままにし、内側に`<div>`を1枚追加してそちらに`display:flex`を指定する。td→div→中身、という二重構造にすることでtableレイアウトとflexレイアウトを両立できる。同様に、rowspanしたセルに`height:26px`のような固定高さを一律指定していると、結合先の行の高さぶんまで自然に伸びず「上段だけに文字がある」ように見えることもある（該当セルだけ`height:auto !important`で解除する）。

### 2026-08-02 — デスクトップ版のスクロール固定ヘッダーは「別テーブルの複製」であり、本体テーブルへのDOM変更が反映されない
kintoneの一覧画面を下にスクロールすると見出し行が画面上部に固定表示されるが、これは本体テーブルの`<thead>`をCSSで固定しているのではなく、`.gaia-app-recordlist-fixedheader`という**別のtable要素に複製**されたヘッダーを表示する仕組みになっている（初期状態では空、スクロールして初めて内容が生成される）。カスタムJSで本体テーブルの列順・列内容をDOM操作で書き換えても、この複製テーブル側は自動追従しない。

**症状**: 列の並び替えなど本体テーブルのthead操作を行うカスタマイズを入れると、スクロールしていない間は正しく見えるのに、下にスクロールして固定ヘッダーが出た瞬間だけ列がズレて見える。

**対処**: 本体theadと同じDOM操作を`.gaia-app-recordlist-fixedheader thead`にも個別に適用する。この複製は生成タイミングが遅い（スクロールして初めて中身が入る）ため、`scroll`イベントリスナーで都度チェックして反映するのが確実（一度適用済みなら早期リターンする軽量な関数にしておけば負荷は無視できる）。

### 2026-08-02 — モバイル版のヘッダー領域（`getHeaderSpaceElement`）は複数カスタムJSが素直に積み上がる「通常のブロック要素」
`kintone.mobile.app.getHeaderSpaceElement()`（デスクトップは`kintone.app.getHeaderSpaceElement()`）が返す要素は、position指定のない通常のブロック要素。複数のカスタムJSがそれぞれ`appendChild`で自分のUIを差し込むと、単純に上から下へ積み上がっていく。

**症状**: 一覧画面全体を占めるような大きなUI（カスタム一覧・ガントチャート等）を先にこの領域へ追加するカスタムJSがあると、後から追加された別のカスタムJS（例: ナビゲーションボタン）はその巨大UIの**下**に配置されてしまい、実質「画面のずっと下」に押しやられて見えなくなる。ファイルのアップロード順（実行順）に依存する問題でもある。

**対処**: ヘッダー領域に依存する小さな常設UI（アイコンボタン等）は、`getHeaderSpaceElement()`に追加するのではなく`document.body`に直接追加し、CSSで`position: fixed`を指定して画面上の固定位置に表示する。こうすれば他のカスタムJSがどれだけ大きなUIをヘッダー領域に積んでも、実行順に関わらず常に見える位置を保てる。

### 2026-08-02 — カスタマイズJSからのファイルダウンロード（`/k/v1/file.json`）は`X-Requested-With`ヘッダーが必須
kintoneのカスタマイズJS内から`fetch('/k/v1/file.json?fileKey=...')`のようにブラウザの`fetch`でセッションCookie認証によりファイルをダウンロードしようとすると、ヘッダーを何も付けない場合`CB_JH01: 認証に失敗しました。セッション認証には、「X-Requested-With」ヘッダーが必要です。`というエラーになる。

**対処**: `fetch(url, { credentials: 'same-origin', headers: { 'X-Requested-With': 'XMLHttpRequest' } })`のようにヘッダーを明示的に付与する。同じ理由で、カスタマイズJSからの一覧取得（`/k/v1/records.json`等）を`kintone.api()`ではなく生の`fetch`で直接叩く既存コードでも、このヘッダーが付いているか確認するとよい（`kintone.api()`は内部で自動付与しているため意識しなくてよい）。

### 2026-08-02 — フィールドコードやラベルに「ルックアップ」と付いていても、実際の型が本物のLOOKUP機能とは限らない
運用歴が長いアプリでは、フィールドコード（またはラベル）が「ルックアップ」となっていても、実際のフィールド型は`SINGLE_LINE_TEXT`（1行テキスト）で、kintone標準のルックアップ機能（他アプリを参照して自動補完・値をコピーする機能）ではないケースがある。名前だけが歴史的経緯で残っている状態。

**症状**: 「ルックアップだから他アプリのレコードとしっかり紐付いているはず」という前提でロジックを組むと、実際には単なる自由入力テキストの一致判定（`like`検索等）に頼っている実装だった、というギャップに気づきにくい。

**対処**: 別アプリとの連携ロジックを触る前に、`GET /k/v1/app/form/fields.json`で対象フィールドの`type`プロパティを必ず確認する（`type === 'LOOKUP'`かどうか）。名前だけで判断しない。

### 2026-08-02 — kintoneのダイアログ（ルックアップポップアップ等）内に独自のテキスト入力を追加する場合、Enterキーで二重発火することがある
カスタムJSでkintoneの標準ダイアログ（`.ocean-ui-dialog`等）内に独自の`<input type="text">`を追加し、`keydown`イベントでEnterキー時の処理（検索実行・ボタンの再クリック等）を実装すると、**ブラウザ標準の挙動と重複して処理が2回走る**ことがある。原因は、そのダイアログ自体が`<form>`要素の一部になっていることが多く、フォーム内のテキスト入力でEnterキーを押すと、ブラウザが自動的に「フォーム内の最初のsubmit/デフォルトボタン」へ仮想的なクリックを発生させる仕様があるため。こちらが`keydown`で実装した独自処理と、ブラウザ標準の仮想クリックが同時に発火し、結果的に同じ操作（ポップアップの再オープン等）が2回実行される。

**症状**: 独自のテキスト入力欄にEnterキーで確定操作を実装したはずが、ポップアップが2つ開く／同じAPIリクエストが2回飛ぶ、等の「二重発火」が起きる。

**対処**: `keydown`（または`keypress`）のEnterキー判定内で必ず`e.preventDefault()`を呼び、ブラウザ標準のフォーム送信・デフォルトボタンへの仮想クリックを止める。`stopPropagation()`は不要な場合が多いが、他のイベントリスナーとの競合が疑われる場合は合わせて検討する。
