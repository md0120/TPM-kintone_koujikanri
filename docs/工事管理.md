# SMC工事管理 kintoneアプリ構築 進捗記録

最終更新: 2026-07-19（app43印刷機能の一旦中止、app45「空調運転記録」新規構築を追記）

## 概要
kintoneを使った工事の施工管理システムを構築中。年度別の案件リストから作業報告書・KY活動記録・協力会社報告書を作成し、完成した作業報告書をLINE WORKSへ送信する仕組みを目指している。

## 決定した要件
- 年度ごとに案件（工事名・工期・担当者）を選べるようにする
- 作業日ごとの作業報告書をkintoneモバイルで作成
- 現場KY用紙・協力会社からの報告書はスマホ撮影して保存
- 案件台帳の詳細画面から「①報告書の作成」「②KY用紙保存」「③協力会社報告書保存」の3つを直接選べる導線にする（関連レコード一覧の「新規追加」機能を利用）
- 編集権限は現場担当者に限定せず、広く編集可能にする
- LINE WORKSへの送信は手動（送信コメント＋日報URLを送る）
- LINE WORKS連携はGAS（Google Apps Script）＋LINE WORKS Bot APIで実装する方針（ユーザーはGAS/Developer Consoleの知識がないため、Claudeが手順を主導）

### 7. kintoneモバイル対応（4アプリ共通の重大な発見と対応）
- **発見した問題**：これまでの全カスタマイズ（検索ボックス、①②③新規作成ボタン、LINE WORKSコピー、工事名リンク等）は、デスクトップ専用API（`kintone.app.*`、`app.record.*.show`系イベント）で作られており、kintoneモバイル（`https://{ドメイン}/k/m/{アプリID}/` で表示される画面、および実機のkintoneモバイルアプリ）では一切動作していなかった
- **原因**：kintoneモバイルは全く別のJS API体系を持つ
  - PC用: `kintone.app.*` ／ イベント名 `app.record.index.show`, `app.record.detail.show`, `app.record.create.show` など
  - モバイル用: `kintone.mobile.app.*` ／ イベント名 `mobile.app.record.index.show`, `mobile.app.record.detail.show`, `mobile.app.record.create.show` など（`mobile.`プレフィックス）
  - ヘッダー領域取得も `kintone.app.getHeaderMenuSpaceElement()`（PC）に対し `kintone.mobile.app.getHeaderSpaceElement()`（モバイル）と別メソッド
- **対応方針（ユーザー確定）**：モバイル版を主軸として今後設計する。PC版は削除せず、そのまま維持・併用する。今後の新機能は基本的にPC・モバイル両対応を標準とする（customize.jsonのdesktop/mobileスロットはPC用ファイルとモバイル用ファイルを完全に独立管理できるため、両対応してもPC側への影響はない）
- **モバイル専用スクリプトを新規作成し4アプリに追加**（PC用ファイルはそのまま残し、削除・変更はしていない）
  - 案件台帳(37)：`工事台帳_検索ボックス_mobile.js`／`案件台帳_新規作成ボタン_mobile.js`／`工事台帳_工事名リンク_mobile.js`
  - TPM作業報告書(38)：`検索ボックス_mobile.js`／`案件自動セット_mobile.js`／`作業日報_LINEWORKSコピー_mobile.js`
  - KY記録(39)・協力会社報告書・他(40)：`検索ボックス_mobile.js`／`案件自動セット_mobile.js`
- **モバイル専用CSSを追加**（案件台帳37のみ現状適用、他3アプリは文字サイズ調整のみ適用）
  - 文字サイズを1段階アップ＋主要項目を太字化（PCは変更なし）
  - 一覧画面の標準ツールバー（案件一覧▾／グラフアイコン／フィルターアイコン）をモバイルのみ非表示化。API（`kintone.mobile.app.showFilterButton`等）は「このステータス画面では実行できません」というプラットフォーム側の制約で使用不可だったため、CSS（`.gaia-mobile-v2-app-index-navigationbar-bodyselector-container { display: none !important; }`）で対応
  - 案件台帳のレコード詳細画面の①②③ボタンに淡い色を付与（①水色 #e3f2fd／②緑 #e8f5e9／③オレンジ #fff3e0）
- **動作確認**：kintoneモバイル画面（`/k/m/{アプリID}/`）で4アプリすべての検索ボックス表示、案件台帳の①②③ボタンからの新規作成・工事名自動セット、工事名リンクからの詳細遷移を確認済み

- **対応方法**：ルックアップ型の設定はAPI経由でも一度設定すると直接解除できない仕様のため、フィールドを削除→同じフィールドコードで通常のテキスト型として再作成する方法で対応

## 技術的な学び・注意点
- kintoneの計算フィールドはDATE_FORMAT関数の結果をそのまま四則演算に使えない場合がある（型エラーになる）。年度計算のような日付演算をする場合は、DATE_FORMATの結果を独立した数値型の計算フィールドとして一度確定させ、それを別の計算フィールドから参照する方が安定する
- kintoneの計算フィールドは、フィールド追加後に既存レコードを開いて保存し直さないと値が反映されない（一括で反映させたい場合は、対象フィールドを含めてExcel/CSVをエクスポート→同じ内容でインポート＝更新することで一括再計算できる）
- kintoneアプリのExcel読み込みで作成した1シートのExcelファイルが「.xlsxとして認識できない」エラーになることがあった。openpyxlで新規作成したファイルはsharedStrings.xmlを持たないケースがあり、xlsxwriterエンジンで作成し直すことで解決した
- kintoneの既定の「（すべて）」一覧ビューは編集・複製・削除ができない仕様。列の並び替えをしたい場合は新規カスタムビューを作成する必要がある
- ブラウザ拡張（Claude in Chrome）経由でのファイルアップロードは、Claude側から任意のローカルファイルを直接指定できない制限がある。ユーザーに一度「ファイルを選択」で該当ファイルを選んでもらう必要がある
- kintoneはPC用とモバイル用で完全に別のJavaScript API体系・イベント名を持つ（`kintone.app.*`と`kintone.mobile.app.*`、`app.record.*.show`と`mobile.app.record.*.show`）。customize.jsonのdesktop/mobileスロットに同じファイルを入れても、モバイル側では対応するモバイルAPIで書き直さない限り一切動作しない
- kintoneのカスタマイズJS/CSSファイルアップロードは、`/k/v1/file.json`で取得した`fileKey`を一度きりしか使えない（desktop/mobile両方に同じfileKeyを指定するとエラー`GAIA_DC04`）。同一内容を両スロットに使いたい場合は2回アップロードして別々のfileKeyを取得する
- kintoneモバイルの`kintone.mobile.app.showFilterButton()`/`showReportSelector()`/`showViewSelector()`は、一覧画面（`mobile.app.record.index.show`内）から呼び出すと「Usage: kintone.mobile.app.showFilterButton(state)」または「The specified JavaScript API cannot be executed on this screen.」という内部エラーで機能しないことを実機テストで確認。標準ツールバーを非表示にしたい場合はJS APIではなくCSS（`display:none`）で対応するのが確実
- kintoneモバイルの一覧画面標準ツールバーのDOMクラスは `.gaia-mobile-v2-app-index-navigationbar-bodyselector-container`（案件一覧▾のビュー選択ボタン・フィルターボタン・インサイト（グラフ）ボタンをまとめて含む）
- ブラウザでkintoneモバイル画面をテストする際、`window.name`は同一タブでのページ遷移・リロードをまたいで値が保持される数少ないグローバル変数のため、イベントが実際に発火したかどうかをリロードをまたいで検証する際のデバッグ手法として有用（`window.location.href`での画面遷移や`javascript_exec`での再読み込みでは`window`オブジェクトの他のプロパティは全て消える）

## 技術的な学び・注意点（追加）
- kintone標準Ganttチャートプラグインの日付ヘッダー固定（スティッキー）機能はCSSの`position:sticky`ではなく、**iframe/ウィンドウ自身のscrollイベントを監視するJS実装**になっている。Ganttをiframe埋め込みする際に「iframeの高さをコンテンツ全体に合わせて内部スクロールを無くす」実装にすると、スクロールイベントが発火せずヘッダー固定が効かなくなる。内部スクロールを保持した固定高さiframeにする必要がある
- 同一originのiframe内の要素に対して親フレームから`getBoundingClientRect()`を呼んでも、返る座標は常にその**iframe自身のドキュメントを基準にしたローカル座標**になる（呼び出し元のJSコンテキストに関係なく）。画面上の真の座標を得るには、iframe要素自体の`getBoundingClientRect()`（これは親ドキュメント基準）を別途取得し、ローカル座標に加算する必要がある
- 要素の位置を数値操作で動かす際、絶対座標を計算で求めるより、「現在の真の描画位置を測定→目標位置との差分（デルタ）を計算→現在のCSS値にデルタを加算する」という差分ベースの補正方式の方が、祖先要素の位置決めロジックを把握できていなくても安全かつ収束しやすい
- **【重要】DOM要素の「現在の表示値」を読み取って何らかの倍率をかけて上書きする処理を、`setInterval`や`MutationObserver`のような繰り返し処理の中で行ってはいけない。** 対象のフレームワーク・プラグインが自身の再描画のたびにDOM要素を作り直す仕様だと、「処理済みフラグ」を要素に付けても新しい要素には引き継がれず、「その時点で既に加工済みの値」を「未加工の自然な値」と誤認して再度倍率をかけてしまい、無限ループで値が指数関数的に膨張する（今回はブラウザのレイアウト上限2^24pxに到達してテーブルが崩壊した）。この種の処理は、初回読み込み時に１回だけ自然な値をキャッシュし、以降は常にそのキャッシュ値を基準に計算するべき
- kintoneカスタマイズJSファイルは、ファイル名が同じでも中身（バイトサイズ）が異なることがあるため、本番とテストアプリで同名ファイルの内容が同じとは限らない。本番に手を入れる前に、実際のファイル内容をダウンロードして差分を確認してから着手する必要がある
- 本番環境への変更は、たとえ「テストアプリで直した内容と同じものを本番にも」という依頼であっても、実行前に変更内容を具体的に提示し、ユーザーからの明確な実行承認（「今すぐデプロイして」等の明示的な指示）を得てから行うべき。「確認してほしい」「了承します」等の曖昧な承認だけでは本番への書き込みを実行しない運用とする

### 40. 【断念】月表示で1日工程バーが隣日にはみ出す問題
- 月次ビュー（1日=30px）では、1日だけの工程でもバー要素の描画幅がラベル文字列の長さに応じて50〜85px程度に拡張され、隣の日まで色付き矩形がはみ出して見える現象が発生（週次ビューは1日の幅が約38.8pxと広いため目立たない）
- `overflow:hidden`によるクリップは効果なし（バー自体の背景色付きボックスのサイズは変わらないため）と判明
- kintone REST APIで各レコードの開始/終了日時を取得し、行内のバー表示順とレコードの日付順を突き合わせて「本当に1日だけの工程」を判定するロジックを実装（DOM上にバーとレコードを結びつけるIDが存在しないため、行単位でのバー数とレコード数が一致する場合のみ突き合わせる方式）。日時データがUTC保存のため、日本時間（+9時間）に変換してから日付を比較するよう修正し、判定ロジック自体は正しく動作することを確認
- しかし`max-width`と`box-sizing:border-box`を組み合わせても、要素の`padding-right`が40pxという想定外の値になっており、実際の描画幅を意図通り縮小できなかった（ブラウザの計算結果が通常のCSSボックスモデルの挙動と一致しない原因不明の現象）。複数回の修正を試みたが解決に至らず、**ユーザー判断でこの機能は中止**。関連コード（`applyMonthClipFix`・`fetchOneDayFlagsByKoji`・`applyOneDayBarWidthFix`とその呼び出し箇所）は全て削除し、安定していた状態に復元済み

## 技術的な学び・注意点（さらに追加）
- **市販/プラグイン製のカスタマイズビュー（HTML+JSで自前レンダリングするタイプ）は、標準のkintone一覧ビューと異なり、URLの`query`パラメータを一覧の絞り込みに反映しない場合がある。** 絞り込みが効かないように見える場合は、まずAPIで該当データのキー値一覧を取得し、DOM上の行を突き合わせて非表示にする「行フィルタ」方式を検討するとよい
- **DOM要素を`appendChild`等で別の親要素に移動（reparenting）させる処理は、対象がサードパーティプラグインの管理下にある場合、プラグインが「子要素が消えた」と誤検知して要素を作り直し、こちらの移動処理と無限ループで衝突し、ブラウザがフリーズする危険がある。** 位置だけを変えたい場合は、DOM構造を変更せずに`position:fixed`＋`top`/`left`座標の指定だけで対応する方が安全（`MutationObserver`は`childList`のみ監視している場合、`style`のみの変更では発火しないため、この方式は無限ループの引き金にもならない）
- 上記の安全な位置調整は、`setInterval`等で毎回同じ計算をやり直す形であれば安全（値が累積・膨張しない冪等な処理のため）。過去に問題化した「現在の描画値を読み取ってさらに倍率をかける」パターンとは根本的に異なる
- ルックアップ型フィールドの「ほかのフィールドのコピー」で指定した**コピー先フィールドは、Excel/CSVインポートの「データの対応付け」画面のフィールド一覧に一切表示されない**（新規作成・更新どちらの用途でも同様）。一括でコピー先フィールドの値を書き換えたい場合は、kintone REST APIを直接使う必要がある
- kintoneの「1ページの表示件数」はビュー設定に存在せず、個人のブラウザ設定に紐づく値のため、管理者側で全ユーザー共通のデフォルトを強制する手段はない
- 日本の祝日データは`pip install jpholiday`で正確に生成できる（2020〜2045年で462件を数秒で生成）。kintoneのAPIやプラグインには祝日情報を持たせる標準機能がないため、必要な場合はこの種のライブラリで生成した静的リストをJS内に埋め込むのが簡単で信頼性が高い
- DATETIME型フィールドの値はUTCで保存される。日本時間の「同じ日かどうか」を判定する処理を書く場合は、必ず+9時間のオフセットを加算してから日付部分を比較する必要がある（UTCのまま比較すると日付境界をまたぐデータで誤判定する）
- CSSの`max-width`＋`box-sizing:border-box`を組み合わせても、対象要素に想定外の大きな`padding`が設定されている等、サードパーティプラグインの内部実装によっては期待通りに描画幅を制御できないことがある。原因の特定に見合わないと判断した場合は、無理に追求せず機能自体を見送る判断も必要

- **真の原因と正しい対応**：このプラグインは、区分フィールドがルックアップ型の場合「表組みを登録済みレコードに限定する」がオフだと、区分（行）の一覧を**ルックアップ先アプリ（app37）の全レコード**から生成する仕様になっている（app43自身に開始日時・終了日時入りのレコードが無くても、app37に登録されていれば行として表示される）。このチェックボックスは元々オフが正しい設定で、オンにする必要は無かった。チェックを外して保存→アプリを更新（プラグイン設定はアプリの「アプリを更新」操作でのみ本番反映される点に注意）で、以前と同じ「年度の全登録案件がデフォルト表示され、開始日時・終了日時が無い工事は行はあるがガントチャートは空白」という仕様に復元
- **教訓**：ガントチャートプラグインの「区分フィールドがルックアップの場合、表示レコードは絞り込みの初期設定に準じる」という設定説明文の意味を誤解し、無関係な問題（削除済みテストデータの行が残る）の対処として関係ない設定を変更してしまった。プラグイン設定を変更する際は、各項目の説明文を正確に理解してから触ること。想定と違う挙動が起きた場合、直前に自分が変更した設定を最初に疑うべきだった
- kintoneのプラグイン設定は、保存しただけでは反映されず、**アプリの設定画面で「アプリを更新」を押して初めて本番へデプロイされる**（フィールド追加等のスキーマ変更と同様、プレビュー状態を経由する）

### 55. app37一覧の「進捗・工事名」列固定＋80%縮小 — zoom方式で複数回失敗し、font-size/padding直接指定方式へ転換

  1. テーブルを独自の`overflow-x:auto`スクロール領域に切り出す方式にしたところ、ヘッダー行とデータ行の縦位置がズレる／完成レコードのグレー行色が消える不具合が発生 → 独自スクロール領域化をやめて素直なページスクロールに戻すことで一旦解消

- 実機で横スクロール・縦スクロール・完成レコードのグレー表示を繰り返し確認し、ズレ・透過なしを確認して本番反映

## 技術的な学び・注意点（zoom + position:sticky の落とし穴）
- **CSSの`zoom`プロパティと`position:sticky`を併用すると、Chromeで固定列のセルがスクロール中〜後にズレて描画される既知の不具合がある。** `zoom`はレイアウトを丸ごと再計算する非標準プロパティで、`sticky`要素は別のコンポジットレイヤーで描画されるため、両者を組み合わせるとレイヤー間の同期がズレる
- 表示縮小と固定列表示を同時に実現したい場合は、`zoom`ではなく**フォントサイズ・パディングを直接縮小する方式**を使うこと。実レイアウト自体が縮むだけなので、スクロール時の再計算が発生せず、`sticky`との組み合わせでも問題が起きない
- 列固定のオフセット計算は、インターバルやMutationObserverで継続的に再計算すると、一度`sticky`化した後のセル幅を基準に計算してしまい誤差が蓄積する。**オフセットは描画イベントごとに一度だけ計算する**のが正しい
- kintone標準の一覧テーブルは、フィールドタイプによって内部DOM構造（クラス名の有無）が異なる。文字列系フィールドには`.line-cell-gaia`という内側ラッパークラスが付くが、ドロップダウン・日付・数値・レコード番号等は付かないため、CSSで一律に対象を絞ると一部のフィールドだけ縮小が効かないことがある。フィールドタイプごとのtdクラス（`recordlist-<type>-gaia`）で個別に対応する必要がある
- 列を固定する際は、セル位置（`nth-child`やcells[i]によるindex指定）ではなく、**フィールドID基準のクラス名**（kintoneが自動付与する`label-<fieldId>`／`value-<fieldId>`）で指定する方が、列の並び替えやレコード操作列の有無に影響されず堅牢
- kintoneの一覧テーブルは、行の縞模様や条件付き色分け（ネイティブの「一覧の色分け」設定）を`<tr>`要素の背景色として適用している。固定列の`<td>`は背景が透過のままだと後ろの列が透けて見えるため、`tr`の`getComputedStyle`背景色を`td`にコピーする対応が必要
- フィールドのデフォルト値をkintoneのフィールド設定で固定値（例：年度＝2026）にしていると、年が変わっても自動更新されない。年ごとに変わる値は、JSカスタマイズで`app.record.create.show`イベント時に動的計算してセットする方が運用ミスを防げる

- kintoneの**アプリ新規作成・フィールド追加をREST API（`/k/v1/preview/app.json`等へのPOST）で行おうとすると、`CB_CS01`（セッション無効）エラーで失敗する**ことがある。既存アプリのフィールド追加・レイアウト変更は過去のセッションでAPI経由で成功した実績があるが、アプリの新規作成自体はUI操作（アプリストア「はじめから作成」）でのみ確実に行えた

- PC版の時刻フィールドをプルダウンに置き換える場合、ネイティブ入力のvalue setter（`Object.getOwnPropertyDescriptor(HTMLInputElement.prototype,'value').set`）経由で値をセットし、`input`/`change`/`blur`イベントを発火させれば、kintoneのレコードモデルに正しく反映される

- kintoneの記録一覧テーブルの各行データにアクセスする際、行データを持つDOM要素は`.recordlist-row-gaia`クラスで判別できる
- ブラウザの印刷ダイアログ（`window.print()`）が開いている間は、Chrome拡張機能によるスクリーンショット取得等のCDP操作がブロックされる（ネイティブOSダイアログが割り込むため）。印刷内容を自動検証したい場合は、実際に印刷する前に`window.print`を一時的にスタブ関数へ差し替え、DOM構造やオーバーレイの見た目だけを確認する方式が有効
- kintoneのカスタマイズJSファイルアップロード後の実機確認で、`window.print`を一時的にモックしてオーバーレイの内容だけをチェックする手法は、印刷ダイアログを開かずに繰り返しテストできるため、印刷系機能の反復開発に有効
